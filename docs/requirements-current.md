- 来源：[原始需求](requirements-original.md)、用户后续补充及本轮采纳的精简建议。
- 本文件是当前需求的唯一正式入口，取代上一版 C01–C50 编号；需求收敛为 V1-01–V1-14，验收按对应功能分组，不再并行维护重复需求矩阵。
- [需求验收标准](acceptance-criteria.md)按首版、能力引入时与后续增强分级；[需求分析](requirements-analysis.md)仅记录设计取舍。

## 1. 产品目标

构建本地自托管的 Agent 任务自动化系统，使用 n8n 编排，Python/FastAPI Runner 执行，SQLite 保存状态，接入 Claude Code CLI 与 OpenAI Codex CLI。

首版交付可实际运行的开发闭环，并以一个本地文档/分析流程证明任务不限于编程。独立任务优先并行，代码成果最终合并；遇到不确定结果可停止并交人工恢复。

## 3. 首版默认方案与使用方式

以下是本轮为缩小范围采用的首版方案，不是用户此前指定的固定技术政策。普通参数可使用默认值并记录；项目可以在支持范围内覆盖配置。

- 以当前 Windows 环境作为首轮开发与验收基准；不据此宣称已支持 Windows 的完整运行链路。
- Docker Compose 先管理 n8n 等服务，Runner 与 CLI 先在主机执行；完整容器化放到后续验证。
- 每个项目配置一个本地专用集成分支，避免直接更新主分支；分支名在创建运行时给出或采用记录在案的默认值。
- 单目标分支采用串行 merge，首版不自动 rebase、squash 或 cherry-pick。
- 默认在执行计划及更新集成目标前提供审批；可显式配置批准计划后自动集成，但必须满足任务 Review、集成检查、未取消和目标未变化等条件。
- 并发数、超时与重试轮数等提供有界默认值；首次运行选择可用 CLI/模型并检查能力，不要求用户手填所有内部配置。
- 保留任务提交、测试/Review 结果、实际配置、错误及产物路径；大体积日志正文可保存在本地文件，由 SQLite 引用。

缺少关键任务输入、目标仓库/分支、必要执行能力或授权时明确停止或等待；不能静默换模型、假定审批通过或扩大权限。具体 CLI 参数以集成验证为准。

## 4. 两条预置流程

### 4.1 开发流程

目标/计划 → 必要审批 → 领取可执行任务 → 创建 Worktree → Coding → 验证 → Review → 必要时 Fix/验证/复审 → 任务 Commit → 串行集成检查 → 按策略批准 → 更新目标分支。

- 前置依赖先用简单任务依赖表达；后继代码任务从包含必要前置成果的基线开始。首版可等待前置任务已集成后再创建后继 Worktree。
- 同一任务不同时运行两个写会话；共享测试端口或目录可使用简单具名互斥，也可直接串行。
- 不自动预测全部文件、接口或代码语义冲突，也不实现通用资源分配器。
- n8n 提供条件、审批和等待语义；Runner 校验节点调用是否合法，并保存执行结果。重复请求不能重复推进同一阶段。
- 只要求实际使用的分支、审批拒绝/超时路径与 Review/Fix 循环行为明确，不设计任意流程语言或插件接口。

### 4.2 本地文档/分析流程

任务输入 → Agent 分析或生成文档 → 基本产物检查 → 按流程独立 Review/审批 → 保存结果。

- 不强制创建 Worktree、Commit 或 Merge；Git 集成与 Git 清理标记为不适用。
- 产物记录路径、版本或内容摘要、生成任务及验收结果，能够交给后继任务使用。
- 首版至少验证一个本地文件产物示例，不要求覆盖所有研究、数据处理或外部系统场景。

## 5. 审查与合并的简化规则

任务 Review 必须使用独立新会话和结构化结论；输出缺失、非法、截断、异常退出或与当前候选不符时不能提交。必要检查由 Runner 收集结果，不能只信 Agent 自述。

任务候选发生变化后，重新执行受影响的检查与 Review。首版使用候选文件/暂存树形成审查输入，不要求为了审查先生成临时提交。

**本轮对机械合并明确例外：** 无冲突、未新增或改写任务代码的 merge，可以复用各任务已有 Review，运行配置的组合检查，不默认再做一次完整 Agent Review。机械 Merge Commit 不因此要求额外独立 Review，但仍须经过集成门禁。

目标 HEAD 在候选验证后前移时，重新计算和验证合并结果，不覆盖新提交。组合检查失败时保留任务成果，目标分支保持上次合格结果。

首版遇到合并冲突停止并保留现场，由人工处理；不实现自动冲突修复。人工解决产生的新内容必须接受新会话的针对性 Review 和必要检查，通过后才能提交与继续集成。项目可对高风险变更显式要求额外 Review。

## 6. 完成、清理与恢复

### 6.1 三类结果

- 任务完成：任务产物满足验收；需要提交的代码任务有通过门禁的提交。
- 集成完成：代码成果进入目标分支并通过组合验收；非 Git 任务不适用。
- 清理完成：适用的 Worktree 和本地任务分支已安全删除；清理失败单独待处理。

这些结果先用简单字段记录，不要求为每项建设独立调度子系统。无需修改的任务记录证据，不制造空提交；部分完成或阻塞不能误放行依赖。

### 6.2 安全清理

首版由人工触发清理。清理前确认没有活跃进程、未提交/未保存改动或资源占用，任务提交已进入目标分支，日志及验收证据已归档到工作区之外。条件不满足时拒绝正常清理并保留现场。

只清理 Runner 管理的任务目录与本地任务分支，不清理无关路径、受保护分支或远程分支。Worktree 与分支步骤分别记录，重复请求检查实际状态；不自动强制删除未集成成果。

### 6.3 有限恢复

首版恢复允许人工介入，不承诺中断会话自动无缝续跑。重启先核对残留进程、工作区、提交/分支和持久状态；结果不明时停止相关任务，供人工确认。

已完成 Commit/merge 但状态未写回时，核对实际 Git 结果再补记或处理；不能盲目重复执行。保留必要操作记录及重复请求保护，不预设通用租约、自动接管、事件投递或分布式协调框架。

## 7. 执行与权限底线

- 暂停后不启动新节点；取消或超时应停止相关进程树，迟到结果不能触发提交/集成。
- 技术重试、Fix/Review 和规划有上限；鉴权失败、需要交互或执行结果不明时进入人工处理。
- 无任务时等待，不反复唤起 Planner；目标完成、依赖阻塞、预算耗尽与人工停止有明确原因。
- 工作目录与 Worktree 不能宣称为安全沙箱。先验证 CLI/执行环境实际权限；无法满足声明的限制时阻止相关运行或明确降低受支持范围，不以提示词替代权限保证。
- 首版不承诺抵御任意恶意仓库的跨平台强沙箱，不向任务暴露无关凭据或 Runner 权威状态写权限。
- 审批与 Review 绑定对应任务/候选；旧内容上的批准不能直接批准新内容。普通输出和配置无需全部版本化成独立实体。
- 先用 Fake Agent 自动测试基础流程，再接入两种真实 CLI 和 n8n 自动循环；不要求首版覆盖所有故障排列组合。

## 8. 后续能力：不阻塞首版

- 多项目同时运行、一个项目跨多个仓库、多机或远程 Worker。
- 任意流程 DSL、复杂汇合策略、运行中流程迁移、可视化编辑器及插件平台。
- 自动冲突修复、更多合并策略、针对 squash/rebase 的成果映射。
- 自动清理调度、保留期管理与远程分支清理。
- 通用资源分配、精确费用硬封顶、自动接管与无缝恢复。
- 外部发送/写入连接器、幂等结果核对和补偿机制；引入具体能力时再实现与验收，未知结果不得盲目重试。
- macOS/Linux 及其他部署方式的实测支持、全容器任务执行和更强隔离。

本轮只调整需求范围。尚未实现服务、执行 Agent 开发任务、修改实际仓库分支或清理资源，也未执行 Commit、Push 或部署。
