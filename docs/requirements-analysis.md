# AgentAutomation 设计取舍

- 更新日期：2026-10-17。
- 本文件解释首版范围取舍，不再重复维护需求编号、完整状态表、数据实体表或验收矩阵。
- 有效范围以 [当前需求基线](requirements-current.md)为准，验证以 [分阶段验收清单](acceptance-criteria.md)为准；[原始需求](requirements-original.md)保留为历史来源。
- 当前仅完成文档，尚未实现或验证 CLI、部署和平台能力。

## 1. 首版解决的问题

让一个本地项目从明确目标出发，拆分任务，在条件允许时并行编码，由新会话审查并按需修复，通过后提交、集成，最终留下可检查的代码和运行记录。另用一个本地文档/分析任务证明任务不依赖 Git 流程。

首版应形成可用闭环，不以实现通用工作流平台、无人干预故障接管或全部平台同时支持作为前置条件。

## 2. 主要取舍

| 主题 | 首版做法 | 后置能力 |
|---|---|---|
| 项目范围 | 注册多个仓库，一次运行一个项目；一个项目关联一个仓库 | 多活动项目、跨仓库任务 |
| 流程 | n8n 预置开发与本地产物流程，可加入基本判断、审批与等待 | Runner 自建流程 DSL、任意插件与热迁移 |
| 节点结果 | 简单执行结果外壳；Review/判断使用必要结构化字段 | 所有输入输出强 Schema、通用产物类型系统 |
| Agent 配置 | 项目→任务→节点覆盖，记录最终 Agent/模型 | 智能选模型、自动优化与复杂回退链 |
| 并行 | 依赖就绪、最大并发和必要具名互斥；独立 Worktree | 自动预测代码语义冲突、通用资源分配器 |
| 合并 | 同一目标分支串行集成，一种保留历史的本地 merge 方式 | 多种合并策略、自动冲突修复 |
| 清理 | 人工触发，检查后清理已集成的本地任务资源 | 保留期调度、自动清理、远程分支清理 |
| 恢复 | 持久记录、启动核对，异常可人工恢复 | 通用租约、自动接管、复杂事件投递框架 |
| 非编程 | 一个本地文档/分析产物流程 | 外部连接器、发送/写入、补偿事务 |
| 平台/部署 | 当前 Windows 环境作为首个验证基准，主机 Runner/CLI，Compose 管理 n8n | macOS/Linux 实测、完整容器执行、远程 Worker |

上述平台和部署是本次收敛采用的首版实施默认方案，不代表已验证兼容性或用户早先指定了该方案。平台可替换，但首版只要求一个选定平台验收；配置接口避免绑定平台细节。

## 3. n8n 与 Runner 的分工

n8n 使用自身的节点、条件、审批等待和循环编排流程，调用 Runner 的有限操作。Runner 保存任务、尝试、审批决定及 Git 操作结果，判断任务是否可领取、是否可提交、是否可集成。

Runner 不需要解析任意流程图，也不重新实现 n8n 的分支汇合语义。重复调用仍需返回可解释结果，不因工作流重试而并发修改同一任务或重复更新分支。

新增审批/判断节点不能绕过 Runner 已有提交、权限和执行上限。首版无需流程热修改；新运行采用新配置，运行中的任务使用启动时保存的有效配置。

## 4. Review 与集成的边界

保留原始规则：任务修改必须通过独立新会话 Review 后才能创建任务提交；Fix 改变内容后重新检查与审查。Review 结构化结果无效时，不能以自然语言“通过”代替。

本次明确收敛旧规则：无冲突且没有新增改写的机械合并，可以复用各任务已有 Review，在集成检查通过后创建所需 merge 提交，无需每次再启动完整 Agent Review。这是对先前“所有集成新提交都先追加审查”的修订，不允许借此提交未经审查的人工/Agent 修改。

冲突时首版保留现场、暂停相关集成，由人工处理；冲突解决产生的修改需新会话针对性 Review，并重新执行检查。项目若有更强审查需求，可在流程中额外添加 Review。

候选内容和目标 HEAD 必须明确；目标分支前移时重新计算并验证，不强制覆盖外部提交。无冲突不保证组合行为正确，所以集成检查仍需保留。首版只承诺配置的实际检查；未配置测试时明确标记验证不足，不伪称测试通过。

## 5. 恢复、清理与权限底线

“可恢复”不等于自动恢复 Agent 对话或无缝继续所有节点。首版启动后先停止新领取，核对旧进程、Git 和 SQLite；能确认的结果补记，不能确认的保留现场，等待人工处理后再继续。

不提前指定租约、事件总线或事务框架。简单持久记录和操作日志即可起步，但必须避免同一工作区两个有效修改者，也不能将未知副作用记为成功。

任务、集成、清理结果可以用独立字段表达，不需要三套复杂状态机。清理失败不否定已完成成果；未保存、未集成或仍被进程占用的资源不得正常删除。首版采用保留提交历史的 merge，避免实现 squash/rebase 的成果映射。

执行对象限定可信本地仓库。仍需使用可验证的 CLI 权限、最小凭据和允许路径；Worktree/cwd 不等于沙箱。首版不承诺抵御任意恶意代码。平台无法满足必需边界时应报告限制或拒绝运行，不能以“可信”虚报隔离。

## 6. 默认值与使用负担

普通配置可以采用默认值，执行记录保存最终值；Agent/模型选择仍需用户项目配置或已记录的 CLI 默认来源。用户显式指定的配置不支持时明确失败，不静默替换。

只有缺少必要输入、执行能力或授权才阻止启动；不要求每个任务都填写不适用的 Schema、资源、预算和产物版本字段。首版预算优先控制次数、时间、Review 轮数和并发，用量与费用可记录但不承诺精确金额封顶。

## 7. 实施顺序

1. 用 Fake Agent 建立 Runner/SQLite、任务依赖、执行限制与基本恢复，跑通开发和本地产物流程。
2. 加入 Worktree 并行、Review/Commit 门禁、串行集成和手动安全清理，验证失败场景。
3. 分别接入两种真实 CLI，验证新会话、模型配置、结果提取及取消。
4. 接入 n8n 的判断、审批、等待和有界循环，完成首版验收。

开发中允许先串行调通，但首版需要证明独立任务可并行；依赖或资源受限时串行是正常调度结果。扩展功能按实际使用需要逐项加入，不阻塞首版。
