- 更新日期：2026-10-17。
- 依据：[原始需求](requirements-original.md)、[当前需求基线](requirements-current.md)及用户确认采纳的补充建议。
- 状态：需求分析与设计建议，尚未实现服务或验证真实 CLI 能力。
- 约定：**已明确**为用户确认的要求；**建议**为尚未确认的实现提案；**待确认**为尚未确定的政策。下文明确标记已采纳的规则属于正式需求；状态枚举、数据表设计、具体默认值和实施路线仍属建议。
- 验收入口：[需求验收标准](acceptance-criteria.md)。

## 1. 定位与本轮变化

**已明确：** 系统支持多个目标仓库注册，第一版运行一个项目；有条件时优先并行，无条件时允许串行。任务不限于编程，可配置流程节点和审批判断，可指定 CLI、模型，并允许 Coding、Review 使用不同 Agent。代码任务可以使用独立 Worktree/分支，成果最终需要合并，支持 Worktree 与分支清理。未来考虑 Windows、macOS、Linux。

这意味着系统需要通用任务执行与成果管理能力，编程闭环作为预置流程。不能再把所有任务都固定成 Coding → Review → Commit，也不能继续将“每项目最多一个写任务”作为默认产品边界。

保留已选定的 Python/FastAPI Runner、SQLite 和 n8n 分工。用户已确认采纳六类补充：并行执行与串行集成、任务/集成/清理分层结果、统一节点契约、项目→任务→节点配置继承、非编程产物验收及副作用重试边界、跨平台执行适配与分平台验证。具体约束见下文及当前需求基线。

建议第一版以配置描述任务流程，优先实现少量实用节点，不提前扩展成任意脚本插件平台或完整可视化流程编辑器。

本轮替代了旧分析中的三项假设：

- 并行从远期扩展调整为调度优先目标；依赖和资源约束决定是否并行。
- 任务成果最终合并成为明确目标；自动合并范围和审批条件仍需确定。
- Agent 按节点配置成为明确能力；每个节点的默认组合尚未选择。

原始需求继续作为历史记录保留；冲突处以当前需求基线为准。最终需要合并不等于本次已授权对实际仓库执行 Merge。

## 3. 系统职责与配置边界

| 组件 | 建议职责 |
|---|---|
| n8n | 配置/发起编排、呈现人工审批、等待和通知；调用 Runner API |
| Runner | 校验流程、领取任务、推进节点、预算与锁、进程管理、结果判定及恢复 |
| SQLite | 权威业务状态、短事务、唯一约束、条件更新与迁移；不在 CLI 执行期间持有写事务 |
| Agent Adapter | 启动新会话、CLI/模型能力检查、输出归一化、错误分类、取消和用量收集 |
| Workspace/Git 管理 | 基线、Worktree、分支、候选快照、Commit、集成、清理及现场核对 |
| 平台执行层 | Windows/macOS/Linux 的路径、进程树、信号、权限与部署适配 |
| 产物与执行环境 | 文件/结果归档；目录、凭据、网络与资源隔离 |

**建议：** n8n 与 Runner 不能各维护一套互不校验的状态机。流程定义需要版本化并交由 Runner 校验，n8n 节点调用只是触发执行或审批的入口。n8n 重启不能改变任务是否可提交、是否已集成的事实。

**已采纳的配置覆盖顺序：** 项目默认 → 任务配置 → 节点覆盖。项目未配置时可使用显式系统默认值；流程模板中的预设值先归入对应层级，不新增隐含优先级。权限和预算仍受上级上限约束，局部覆盖不能提权。每次执行保存最终解析后的 Agent、模型、参数、提示模板版本、权限、超时和预算快照；默认组合与可回退选项仍待配置。

不能把一个 CLI 的模型名或参数直接传给另一个 CLI。精确参数和受支持模型需经 Adapter 验证；不支持时明确报错或进入预先配置的回退路径，不能静默换模型。

## 4. 流程节点与非编程任务

### 4.1 统一节点模型建议

第一版建议支持下列节点，不要求每个任务全部使用：

| 类型 | 用途 | 关键约束 |
|---|---|---|
| Agent | Planning、Coding、Review、Fix、研究、分析、文档处理等 | CLI、模型、新会话、输入和输出 Schema、权限范围 |
| Validation | 测试、格式/文件校验、数据约束、验收检查 | Runner 收集结果；受控命令/校验器和资源范围 |
| Condition | 按结构化结果选择后继路径 | 有限、可校验表达式；不能任意执行 Python 或 Shell |
| Approval | 等待人工批准、拒绝或要求修改 | 绑定具体节点、输入版本和产物；定义拒绝、超时与失效处理 |
| Git operation | 工作区准备、提交、集成与清理 | Runner 专属权限；不能绕过 Review/审批门禁 |
| Wait | 等待事件、外部条件或时间 | 持久化唤醒条件，不能忙循环 |

**已采纳的节点契约：** 节点必须明确输入/产物引用及 Schema、验收规则、前置依赖、Agent/CLI/模型（适用时）、权限、资源、超时、重试、预算和副作用类别；定义成功、失败、拒绝与跳过后的路由。审批节点明确拒绝、要求修改、超时及失效处理。

**已采纳的流程约束：** 分支必须定义汇合条件，循环必须配置显式上限，未选中节点应能跳过而不造成永久等待。n8n 提供编排及审批入口，Runner 持久化并校验实际转换，不能通过新增节点绕过门禁。

**实现建议：** 任务依赖与节点依赖分别表达，无环图描述前向依赖，Review → Fix → Review 使用有界迭代。第一版先使用配置文件/API；编辑入口与是否需要拖拽编辑器尚未确定。

任务开始后固定流程、输入和验收版本；编辑模板影响新运行。修改正在运行的流程需生成新版本，在安全边界迁移并重新校验受影响批准，不得让旧审批批准新内容。

### 4.2 非编程任务建议

**已采纳：** 非编程任务不强制绑定 Git 仓库、Worktree、Commit 或 Merge，按产物与流程验收完成。产物必须记录类型、位置、内容摘要、版本、生产节点和验收证据；Review 可针对文件、报告或结构化结果。具体首批任务类型仍待确定，研究、报告、文档和数据处理仅为示例。

任务完成、集成完成、清理完成分别记录；非 Git 任务的 Git 集成与 Git 清理标记为不适用，不因此阻塞完成。代码任务的任务完成需要合格提交，最终交付还要求集成验证通过。清理失败不改变已经成立的任务或集成结果。

**已采纳的外部副作用边界：** 发消息、写外部系统等动作需单独授权，并具备幂等机制或可核对执行结果；结果不明时不得盲目重试。具体连接器不在本轮默认范围内，本次文档更新不授予外部操作权限。补偿操作如何定义仍属后续设计。

## 5. 并行调度与共享资源

**已明确：** 第一版只运行一个项目，不等于该项目只能执行一个任务。独立任务满足条件时应优先并行；不能并行时可串行。

**建议并行准入：** 依赖已满足、输入版本固定、预算已预留、执行环境支持、并发额度可用、所需资源锁无冲突。并发上限配置化；具体数值应按主机、CLI 限流和费用情况确定，不写死为产品要求。

- 文件修改任务使用各自 Worktree；同一任务工作区同时只有一个修改者。
- 测试可能共享端口、数据库、缓存或输出目录，需要独立资源或显式资源锁；文件不重叠不代表可安全并行。
- 预算/调用额度在领取时原子预留，完成后结算；多个任务不能同时透支剩余额度。
- Worktree 创建、分支更新和清理等共享 Git 元数据操作按仓库协调。
- 合并同一目标分支必须串行，并在执行时重新检查目标 HEAD。
- 没有可并行任务或能力不足时串行推进，并记录依赖、资源或平台原因。

不建议第一版预测所有代码语义冲突。优先支持依赖独立、资源声明清晰的并行任务，最终由集成验证发现组合问题。

## 6. 成果合并、依赖衔接与清理

### 6.1 已采纳的合并流程

**已明确：** 任务成果最终需要合并；向同一目标分支串行集成，合并结果必须重新验证。**待确认：** 具体目标分支、集成方法、自动放行条件及审批点。原文“默认禁止自动 Merge”已经调整为受策略控制的合并能力，不代表无条件自动合并。

流程要求为“并行开发和任务审查 → 合格任务提交 → 串行集成队列 → 形成集成候选 → 组合测试及必要 Review → 按策略审批或自动放行 → 更新目标分支 → 按保留策略清理”。任务通过不等于项目已交付；记录任务提交、集成记录和最终目标提交。

**建议默认目标：** 项目专用集成分支；进入 main 等最终分支另设审批。是否采用这一默认值仍待确认。Push、部署继续默认禁止，与本地合并分别控制。

已采纳的集成规则（第 7 项为实现保护建议）：

1. 任务从明确的基线派生；后继任务的基线必须包含其需要的前置成果，不能只看数据库中的“完成”。
2. A/B 在各自基线上通过 Review，不证明合并结果通过。集成后必须验证组合行为，尤其是同名配置、接口和数据库变化。
3. 合并候选在隔离集成工作区形成；目标分支前移后，旧候选与批准失效，重新计算和验证，不覆盖外部提交。
4. 冲突进入人工处理或明确限轮的 Fix 流程；冲突解决会产生新候选，重新测试和 Review。
5. 如果生成 Merge Commit 等新提交，提交前审查其候选树；已有任务提交均需已通过各自门禁。不得为了适配合并而绕过“Review 后才能 Commit”。
6. 集成队列失败应保留任务成果，阻塞相应后继或交付，不能把目标分支更新到失败候选。
7. 明确主工作区脏文件/分支被其他 Worktree 占用时的策略；建议不强制切换或覆盖用户现场。

依赖边建议区分“只需要前置产物”“需要前置已审查提交”“需要前置已集成”。第一版可先支持必要的两类，避免所有依赖都必须等待全局合并。

### 6.2 Worktree 与分支清理要求

**已采纳：** 任务、集成、清理分别记录结果；清理失败不否定已完成成果。正常清理前必须确认没有活跃进程、未保存或未集成成果，且已归档日志及验收证据；失败现场按保留策略处理，不能直接删除。具体保留期、自动触发与审批政策仍待确定。

建议进一步采用以下实现检查：

- 工作区没有活跃进程或待恢复尝试，没有未提交/未跟踪成果需要保留。
- 已核验任务成果进入目标提交；采用 squash/rebase 时不能只用 Git 祖先关系判断，需保存旧提交与集成结果映射及验证证据。
- 日志、Review、测试结果、任务提交与集成证据已存到工作区之外。
- 删除路径属于 Runner 管理的指定工作区，分支属于该任务且未被占用；不得删除用户目录、受保护或无关分支。

支持手动清理和配置化自动清理；自动执行条件、保留期与审批政策待确认。默认建议保留失败、取消、冲突和未集成成果，先提供清理预览；强制删除另行授权。

清理失败只记录待重试原因，不回滚已完成的集成。Worktree 清理与分支删除分步记录；重复请求应能识别已删除目标，不误删新创建的同名资源。

## 7. 状态、持久化与恢复

### 7.1 状态建议

| 层级 | 建议状态/信息 |
|---|---|
| Run | RUNNING、WAITING、PAUSING、PAUSED、CANCELLING、CANCELLED、COMPLETED、FAILED、STOPPED |
| Task | PENDING、READY、RUNNING、WAITING_APPROVAL、BLOCKED、SUCCEEDED、FAILED、CANCELLED |
| NodeRun/Attempt | QUEUED、RUNNING、SUCCEEDED、FAILED、TIMED_OUT、CANCELLED、SKIPPED、RECOVERY_REQUIRED；重试创建新 Attempt |
| Integration | PENDING、VALIDATING、WAITING_APPROVAL、INTEGRATED、CONFLICTED、FAILED |
| Workspace lifecycle | ACTIVE、RETAINED、CLEANUP_PENDING、CLEANED、CLEANUP_FAILED |

上述状态仍需在实现时收敛合法转换。业务结果与执行结果分开：Review 返回 `changes_requested` 可以代表节点正常执行完成，但需路由到 Fix。无需修改、部分完成和阻塞也不能单凭 CLI 退出码判为交付成功。

### 7.2 数据实体建议

- Project/Repository：注册、仓库路径、运行环境、目标分支、权限和项目关系；一项目是否允许多仓库待确认。
- WorkflowDefinition/Version、NodeDefinition、Edge：流程版本、输入输出契约、路由、预算与权限配置。
- Run、Task、TaskDependency、NodeRun、Attempt：运行、任务、依赖、节点实例与每次新会话的完整证据。
- Workspace、Candidate、Artifact：Worktree/非 Git 工作区、代码或通用产物版本与摘要。
- ReviewResult、ValidationResult、Approval：判定、证据和绑定对象及有效期。
- IntegrationRecord、CleanupOperation：前后提交、集成方法、冲突/验证、任务提交映射、清理条件与结果。
- Operation/Event/ResourceLease：幂等键、操作意图、事件投递、资源租约与执行代次。
- Usage/Log：预算预留和结算、用量来源、脱敏日志索引及保留策略。

建议 SQLite 保存权威状态、日志索引和有界内容，大体积输出存持久化产物目录；纯数据库存全部日志的需求仍需确认。n8n 自身存储与 Runner 数据库分别管理；数据库放本地持久卷，避免网络共享目录。

### 7.3 一致性与恢复建议

SQLite 事务不能覆盖 CLI、Git 和外部副作用。采用“记录意图 → 执行 → 核对证据 → 推进状态”，不承诺任意故障下严格执行一次。

领取采用条件更新与唯一约束；租约过期先查旧进程，不能立即重跑。PID 之外记录进程身份和执行代次，拒绝旧 Worker 迟到结果。Commit/合并已成功但状态未写回时，检查实际分支和提交后补记；状态不明进入人工恢复。

对不可幂等的外部操作，先核对执行凭据再决定补记或重试。清理、审批回调、事件和节点请求均需去重；事件丢失通过低频核对补偿。

## 8. Review 与完成门禁

**建议统一结果协议：** 严格版本化 Schema，至少包含任务/节点/尝试标识、候选产物版本、结论、问题列表和验收证据引用。Review 结论可为 `pass`、`changes_requested`、`unable_to_review`；非法 JSON、截断、异常退出、证据缺失或候选不匹配都不能通过。

这是 Runner 内部协议，不假设两种 CLI 原生格式相同。不能扫描自然语言中的“通过”或“LGTM”作判定。

代码 Commit 前建议同时满足有效执行代次、当前需求/候选对应的 Review、Runner 必要验证、审批与预算条件。候选覆盖新增/修改/删除/二进制和暂存内容；提交后核验提交树、父提交和目标分支。测试、人工修改或 Fix 改变内容时批准失效。

Git hooks 和签名程序纳入可信执行策略，不静默跳过已要求 hooks。提交已发生但后验不一致时保留现场并阻塞下游，不假定数据库回滚撤销 Git。

非 Git 任务按产物校验、独立 Review 和流程审批判定完成，不制造空 Commit。建议任务范围和验收标准版本化，Agent 不得通过删测试或放宽标准自行降低完成条件。集成交付另外检查最终目标分支及组合验收。

## 9. 控制、权限与跨平台

### 9.1 控制建议

- 暂停：阻止新节点启动，当前节点按政策结束后停在安全边界；暂停期间不推进提交/集成。
- 取消：终止整棵进程树，确认停止后结束，保留现场；不能保证撤销已经发生的 Commit 或外部操作。
- 超时/重试：按错误分类进行有界退避；鉴权、交互输入、未知副作用进入人工处理，不无限重试。
- 预算：技术重试、Fix、Review、规划次数分别计数，受 Run 总限额约束；并发预留额度。
- 等待/停止：依赖、审批、事件等待持久化；目标完成、无进展、预算用尽和人工停止记录不同原因，禁止空转。
- 审批：定义通过/拒绝/要求修改/超时，绑定版本；变化后失效。具体审批人、入口与有效期待配置。

所有无人值守命令应采用可控非交互方式。实时费用/Token 与硬封顶取决于 CLI 实测能力；不能用事后估算承诺精确费用上限。

### 9.2 权限建议

Worktree 不是安全沙箱；Agent 不拥有 Runner 数据库、审批与 Git 集成权限。按目录、执行身份、凭据、网络和资源约束权限。Review 尽可能只读，动态验证在隔离副本中执行。外部资料、仓库指令和插件不能扩大权限。

FastAPI 和审批回调需要鉴权与幂等校验；日志脱敏。不默认授予 Push、部署权限；Runner 的合并/清理操作仅按已配置政策执行。

### 9.3 跨平台要求与实现建议

**已采纳：** 通过平台执行层处理 Windows、macOS、Linux 的路径、Shell、进程树终止、文件锁、权限和凭据差异；按平台实测并声明支持范围，不将可移植设计等同于已验证支持。**待确认：** 首发平台、三个平台的支持时间和主机/容器部署方式；本轮不增加多机远程调度要求。

**实现建议：** 使用参数数组、明确 cwd/编码、可配置可执行路径；分别适配 Windows 进程树与 POSIX 进程组，补充路径大小写、符号链接和换行处理。测试覆盖空格/中文路径、取消、Worktree 和清理。

Compose 保留为部署选项；Runner/CLI 全容器或主机原生/WSL 的边界仍需选择。主机可移植不等于已有跨机调度；第一版不因此引入远程 Worker 平台。

CLI 预检记录版本、模型支持、新会话、非交互、权限、结果格式、认证、取消及用量能力。每个平台分别声明测试状态，不在未验证时承诺三平台功能等价。

## 10. 分阶段交付建议

| 阶段 | 范围 | 完成标准 |
|---|---|---|
| M0 | 流程/产物协议、合并审批政策、平台与 CLI 可行性 | 核心未决项有决策记录，能力声明有实测依据 |
| M1 | Runner/SQLite、少量流程节点、Fake Agent、并行调度、串行集成、清理和恢复 | 编程与非编程示例均可运行；资源冲突自动等待或串行；故障可恢复 |
| M2 | 两种真实 CLI、节点 Agent/模型配置 | 同一契约测试及小型任务验证；明确不支持能力 |
| M3 | n8n 编排、判断/审批、等待/通知、部署 | 流程与 Runner 状态一致，重复回调不重复执行 |
| M4 | 自动规划、并行策略完善、有界修复/自动循环 | 有界目标持续推进，空队列/无进展/预算耗尽可稳定等待或结束 |
| M5 | 复杂集成、更多任务节点、更多平台验证与展示 | 按独立验收扩大支持范围 |

可逐步实现，但不能把“所有任务固定串行”作为最终第一版验收。若首轮技术验证只能串行，应记录原因和并行能力的交付缺口。无需提前建设复杂 UI、跨机集群或任意插件生态。

## 11. 重点验收场景

| ID | 场景 | 预期 |
|---|---|---|
| A01 | 注册多个仓库，第一版有一个活动项目 | 不误启动第二项目；独立任务满足条件时并行 |
| A02 | 任务存在依赖或共享端口/数据资源 | 后继等待正确基线，资源冲突按锁等待或串行 |
| A03 | 同一任务节点选择不同 CLI/模型 | 配置优先级可追踪，新会话；无效模型不静默降级 |
| A04 | Review → Fix → 复审，含非法输出/异常退出 | 有界循环；无有效通过结果不能提交 |
| A05 | 审查/审批后修改候选或流程 | 旧批准失效；迟到回调不能批准新版本 |
| A06 | 并行分支分别通过但组合测试失败 | 集成候选被阻止，目标分支保持上次合格版本 |
| A07 | 集成目标前移、发生冲突或 Runner 中途崩溃 | 串行核对、重新验证或等待处理，不覆盖外部修改 |
| A08 | Commit/合并成功而数据库未写回 | 恢复识别实际提交，不重复制造副作用 |
| A09 | 清理含活跃进程、未提交或未集成成果的工作区 | 正常清理拒绝；成果与证据保留 |
| A10 | 已完成集成后清理部分成功、重启或重复请求 | 可补做剩余步骤，不误删无关资源 |
| A11 | 非编程任务产出报告或结构化数据 | 无 Git 节点也可验收；结果可追踪并供后继消费 |
| A12 | 非幂等外部动作返回超时/未知结果 | 核对凭据或人工处理，不能自动重复发送/写入 |
| A13 | 暂停/取消与并发节点、子进程、迟到结果交错 | 权威状态可核对；停止后不推进 Git 操作 |
| A14 | 多任务同时接近预算/CLI并发上限 | 原子预留，限制不被并发突破；达到停止条件有原因 |
| A15 | 空队列、审批等待、无进展 | 持久化等待或明确结束，不重复唤起 Planner |
| A16 | Windows/macOS/Linux 的路径和进程行为 | 在已支持平台完成创建、取消、恢复、集成和清理测试 |
| A17 | 审批被拒绝/超时，条件分支跳过后汇合 | 走配置路径，不误启动被拒绝节点，不永久等待已跳过分支 |
| A18 | 节点覆盖任务和项目的模型配置 | 项目→任务→节点顺序生效，保存有效配置，回退必须显式记录 |
| A19 | 任务和集成完成后清理失败 | 已有完成结果保留，清理单独待重试；非 Git 集成/清理标记不适用 |
