## 1. 交付目标与实施原则

首版交付一个可在选定 Windows 环境运行的本地系统：主机运行 Runner/CLI，Compose 管理 n8n；支持单活动项目内独立任务并行、独立审查、有界修复、任务提交、串行集成、人工冲突处理和手动安全清理。另提供一个无需 Git 的本地文档/分析流程。

先以 Fake Agent 和临时仓库跑通基础流程与主要失败场景，再逐一接入真实 CLI，最后接入 n8n 自动循环。基础模块开发期间不要求真实 Agent 可用。

- 依赖就绪且文件边界清晰的开发任务并行推进，共享契约由一位负责人维护。
- n8n 负责流程分支、审批等待及循环；Runner 负责任务领取、有限阶段操作、持久状态和门禁，不解析任意流程图。
- 调度只判断简单依赖、并发额度和必要具名互斥，不开发通用资源调度器。
- 新会话通过材料交接上下文，不恢复旧 Agent 对话。普通输出可为文件，只有机器决策需要严格结构。
- 每个任务伴随必要测试；不等到最终装配才验证 Git 门禁和进程取消。
- 未确认副作用可停下交人工处理，不以自动接管、所有故障组合或三平台同期支持为首版门槛。

## 2. 建议工程结构

采用 Python 3.11+、FastAPI、Pydantic、SQLite 和 pytest；具体依赖版本在工程初始化时选择兼容版本并锁定。SQLite 初期使用 Python 标准库，不引入额外消息队列或分布式基础设施。Windows 进程树控制所需库通过能力验证决定。

```text
pyproject.toml
src/agentautomation/
  app.py                 # FastAPI 与生命周期，有限操作入口
  config.py              # 项目→任务→节点覆盖与默认值
  models.py              # 共享请求/结果、必要状态、Review 协议
  db.py                  # SQLite、执行记录、条件领取、请求去重
  process.py             # 子进程、日志、超时与进程树取消
  runtime.py             # 依赖领取、阶段门禁、检查、限额和恢复
  workspace.py           # Worktree、候选、验证与任务 Commit
  integration.py         # 串行 merge、人工冲突、手动清理
  agents/
    base.py
    fake.py
    claude.py
    codex.py
workflows/               # n8n 开发与本地产物流程
deploy/                  # Compose 配置与部署材料
examples/                # 最小配置、示例输入和测试仓库生成说明
tests/                   # 单元、临时仓库集成与有限端到端测试
docs/                    # 安装、运行、恢复、清理说明与能力记录
```

目录只是分工建议，不要求每个概念都成为服务或独立数据表。生产数据库、Worktree、日志和产物存放在配置的数据目录，不混入源码或自动提交。

### DEV-01 的验证范围

早期只做能力探测，不启动完整真实开发闭环；登录、付费调用或实际仓库操作需具备对应授权。可以先检查版本与文档，把不能安全验证的项目标成待验证。

- CLI：按实际版本确认非交互调用、指定模型、新会话、最终结果读取、退出码和工具权限，不预写猜测参数。
- Windows：可执行文件发现、`.exe`/`.cmd` 启动、参数数组、中文/空格路径、编码、进程树取消。
- Git：提交身份、必要 hooks/签名的非交互行为、Worktree 路径与目标分支可用性。首版自动运行要求已有初始提交；空仓库需先由操作者初始化，不扩展专用初始化系统。
- 部署：Docker/n8n 版本、容器访问主机 Runner 的地址与最小鉴权；不能把容器内 localhost 当作主机。只在确有需要时开放指定接口，不默认暴露公网。

CLI 缺少原生 JSON 约束时可由 Adapter 提取最终结果并严格校验；无法可靠判断就阻止 Review 通过。费用信息缺失可记录未知；明确模型不支持、新会话无法保证、必要权限或取消能力无法兑现则阻塞对应路径，不能标记为已完成。

## 4. 关键接口与分工约定

DEV-02 先冻结四类小接口，后续开发者不同时修改公共契约；需要调整时由主负责人统一协调：

1. 执行输入与结果：任务/尝试标识、阶段、cwd、有效 Agent/模型配置、输入材料；结果仅含状态、产物引用、错误和可用用量。
2. Review 结果：候选标识、结论、问题列表和必要证据引用；用状态字段作路由，不解析“LGTM”等自然语言。
3. Git 操作：准备 Worktree、收集候选、验证并提交、准备集成候选、应用合格集成、检查并清理。Git 操作本身不接受 Agent 自行批准。
4. 持久化/服务操作：注册、创建运行、领取任务、启动阶段、提交结果/审批、控制和查询；同一逻辑请求可重复读取结果，不重复启动有效操作。

有限阶段调用返回操作标识，由查询读取进度，不在 HTTP 请求中等待整个 Agent 会话。n8n 持有流程路由，Runner 保存操作事实和审批决定。初期不增加通用工作流 Definition/Edge 引擎。

n8n 负责持续请求可执行任务；Runner 根据并发额度选择并启动有限尝试，不自行运行第二套无限自动规划循环。任务完成后以状态查询与受控等待驱动下一轮，队列空时停止调用 Agent。

## 8. 首版配置与开发前提

可直接采用的工程默认值：最大并发 2、单项目专用本地集成分支、计划与集成前审批、无自动模型回退、日志正文保存在本地文件。时间/次数/轮数限额在测试配置中给出有限值，之后随项目调整。默认值是计划选择，不新增产品硬限制。

真正阻塞对应集成任务的输入只有：可用的 CLI/模型及认证、必要权限/取消能力、目标仓库已有 Git 基线、实际测试命令，以及 n8n 受控访问主机 Runner 的条件。缺少这些不阻塞 Fake 基础开发。

无测试命令时记录“未执行项目测试/验证不足”，不得标记测试通过；自动集成只在项目明确定义允许的检查与放行条件后启用。示例仓库提供最小检查，保证首版验收有实际验证证据。

计划不要求现在完成登录、支付调用、真实仓库合并或删除。后续实施使用一次性测试仓库验证副作用，针对用户仓库的操作仍遵循运行配置和授权。

## 9. 排期与完成定义

按 M0→M1→M2→M3→M4 排期；先完成接口冻结，再按第 5 节并行。关键路径主要经过 DEV-02→03/04/05→06/07→09→10→11，真实 CLI 的能力问题是另一条可能延长交付的路径。

不在能力探测前承诺精确日期。完成 M0 和 M1 后，依据实际吞吐更新每项剩余工作；CLI 适配、Windows 取消、Docker→主机连接单列不确定性，不按并行人数直接除工期。

首版完成必须同时具备：12 组验收通过、实际启用条件能力通过、两种 CLI 的版本/配置记录、两个可复跑示例、可证明并行与合并的证据、最小安装运行说明，以及一页人工冲突处理/恢复/安全清理说明。

不能将两种 CLI、并行、合并或取消标为“不适用”来通过首版验收。外部连接器、新平台、自动清理、自动接管和完整容器执行不阻塞本版。

本轮已先实现 UI 与 Fake Runner/n8n 接入薄层；接入状态和未完成验证见文首及 [n8n 接入说明](n8n-integration.md)。DEV-01–DEV-11 的完整验收仍待推进，尤其真实进程执行、Review/Fix、Worktree/提交/集成、真实 CLI 与重启恢复；不直接接入无人值守真实 Agent 循环。
